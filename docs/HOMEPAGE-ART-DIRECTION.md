# แผนปรับหน้าแรกและความอ่านง่าย

วันที่: 4 ตุลาคม 2026 · สถานะ: ลงมือปรับตามแผนแล้ว · ผลตรวจอยู่ท้ายเอกสาร

## 1. ปัญหาและเป้าหมาย

หน้าแรกปัจจุบันใช้กล่องและพื้นที่ว่างคล้ายเครื่องมือจัดการงานมากกว่าเว็บค้นหานักวาด ภาพประกอบมีเพียงแบบเดียวและไม่มีสิ่งให้ลองเล่น ข้อความรอง 9–14px รวมถึงช่องกรอกที่ย่อบน desktop ทำให้อ่านยากบนจอ PC 24 นิ้ว

เป้าหมายคือให้ผู้มาใหม่เข้าใจว่า “มาหาคนทำงานอาร์ตที่เข้ากับไอเดียของเรา” ภายในหน้าแรก พร้อมค้นหาหรือเลือกหมวดได้ทันที และคงทางเข้าฝั่งครีเอเตอร์ไว้ชัดเจน ขนาดจอจริงขึ้นกับ resolution และ scaling จึงใช้ viewport 1920×1080 เป็นกรณีหลักของ PC และตรวจขนาดอื่นร่วมด้วย

## 2. Art direction: โต๊ะทำงานของนักวาด

- พื้นกระดาษสีอุ่น เส้นหมึกม่วงเข้ม แต้มสีเหลือง คอรัล และมิ้นต์; dark mode ใช้พื้นหมึกและคงสีภาพให้สด
- Hero แบ่งเป็นข้อความกับกระดานภาพ: หัวเรื่องใหญ่มีเส้นขีดวาดมือ กรอบภาพเหลื่อมเล็กน้อย เทปและสติกเกอร์เป็นของตกแต่ง
- ภาพเวกเตอร์ออกแบบในโปรเจ็ค ไม่เพิ่มบริการภาพภายนอก และไม่ใช้ผลงานของครีเอเตอร์โดยไม่ได้รับอนุญาต
- ภาพตัวอย่างระบุว่าเป็นภาพประกอบ แยกจากร้านจริง ไม่สร้างรีวิว ยอดขาย จำนวนผู้ใช้ หรือสถานะคิวปลอม
- การเคลื่อนไหวเกิดเมื่อกดหรือ hover เท่านั้น ไม่มี carousel อัตโนมัติ ไม่มีแอนิเมชันวนที่แย่งความสนใจ; รองรับ reduced motion

## 3. ลำดับเนื้อหาและลูกเล่น

1. **Hero + ค้นหา:** ข้อความสั้น ชวนเอาไอเดียมาทำเป็นงานจริง ช่องค้นหาเด่น คำแนะนำประเภทงานอยู่ใกล้กัน
2. **Art playground:** เลือกภาพ Portrait / Chibi / Emote และเลือกชุดสี 3 แบบ; ภาพเปลี่ยนทันที มีปุ่มไปหาครีเอเตอร์ในหมวดที่เลือก ใช้ได้ด้วยเมาส์ สัมผัส และคีย์บอร์ด
3. **เลือกประเภทงานจากภาพ:** 3 การ์ดภาพที่มีบุคลิกต่างกันและลิงก์ไปตัวกรองจริง ลดการอ่านกำแพงข้อความ
4. **ครีเอเตอร์:** คงข้อมูลร้านจริงและ empty state ที่ซื่อสัตย์; ไม่มีงานจริงก็ยังมีภาพและหมวดให้สำรวจ
5. **วิธีสั่งงาน:** 3 ขั้นตอนพร้อมหมายเลข ไอคอน และพื้นลายเส้น; ลำดับชัดบน mobile
6. **ความมั่นใจ + เปิดร้าน:** รักษาข้อเท็จจริงเรื่องราคา เงื่อนไข และติดตามงาน; ปิดท้ายด้วยพื้นที่ชวนครีเอเตอร์เปิดร้านที่มีสีและบุคลิกเดียวกับ hero

## 4. ขอบเขต implementation

- หน้าแรกยังเป็น Server Component เพื่ออ่านร้านจริง; แยก Client Component เฉพาะ playground ไม่ส่งข้อมูลร้านหรือ dictionary ทั้งก้อนไปเพิ่มโดยไม่จำเป็น
- รวมข้อความ TH/EN ใน dictionary เดิม ทุกปุ่มมีชื่อที่เข้าใจได้ และสถานะที่เลือกสื่อด้วยขอบ/เครื่องหมายควบคู่กับสี
- ไม่เพิ่มแพ็กเกจ animation หรือ carousel; ใช้ CSS, SVG และ React ที่มีอยู่
- การค้นหาและลิงก์หมวดคงพฤติกรรมเดิม ไม่แตะคำสั่งซื้อ การชำระเงิน สิทธิ์ หรือข้อมูลผู้ใช้

## 5. ความอ่านง่ายและ responsive หลังจัดหน้าแรก

- ใช้ rem: caption 14px, small 15px บนมือถือ / 16px บน desktop, body 16px / 17px; หัวเรื่องมีเพดาน ไม่ขยายตามความกว้างจอไม่สิ้นสุด
- เพิ่มความสูงปุ่มและช่องกรอกทั่วไปเป็น 44px และปุ่ม compact เป็น 40px; ช่องกรอกไม่ย่อฟอนต์บน desktop
- เพิ่มระยะบรรทัดภาษาไทย ลดข้อความขนาด 9–11px และเพิ่มความเข้มข้อความรอง
- Mobile เรียงเนื้อหาเป็นคอลัมน์เดียว; แผงภาพและปุ่มไม่ล้นในจอ 320px; เมนูเต็มแสดงเมื่อมีพื้นที่จริง
- ตรวจ select/tabs/dialog และจุดที่มีข้อความยาว; dialog เลื่อนภายในได้เมื่อจอสั้น; ข้อความในห้องงานตัดบรรทัดได้
- ตรวจ layout สองคอลัมน์ของหน้าคำสั่งซื้อและบริการ ไม่บีบเนื้อหาที่ breakpoint กลาง

## 6. เกณฑ์ตรวจรับ

| เรื่อง | เกณฑ์ |
|---|---|
| บุคลิกหน้าแรก | มีภาพหลายแบบ สีและลายเส้นชัดเจน ไม่พึ่งข้อความอย่างเดียว |
| ลูกเล่น | เปลี่ยนสไตล์/ชุดสีได้จริง ปุ่มค้นหาส่งไปหมวดตรงกับตัวเลือก |
| คีย์บอร์ด | เข้าถึงตัวเลือกด้วย Tab และเลือกด้วย Space/Enter หรือปุ่มลูกศรตาม semantic control; focus มองเห็น |
| Responsive | ตรวจ 320, 390, 768, 1024, 1440, 1920 และ 2560 CSS px; ไม่มีหน้าเลื่อนแนวนอนโดยไม่ตั้งใจ |
| ภาษา/ธีม | ตรวจ TH + EN และ light + dark; label ไม่ถูกตัด |
| ฟอร์ม | ข้อความอย่างน้อย 16px, label อ่านได้, ปุ่มหลักสูงอย่างน้อย 44px |
| ข้อมูลจริง | ค้นหา/หมวด/ร้านตัวอย่างใช้เส้นทางเดิม; ไม่สร้างข้อมูล production เพื่อทดสอบ |
| Regression | lint, typecheck, tests และ production build ผ่าน |
| การปล่อย | ตรวจ diff → commit/push ตามที่ผู้ใช้อนุญาต → ตรวจ CI และ Vercel ของ commit นี้ |

## 7. ผลตรวจและข้อจำกัด

### ผลที่ตรวจในเบราว์เซอร์ (4 ต.ค. 2026)

- หน้าแรก TH/light และ EN/dark: 320, 390, 768, 1024, 1440, 1920, 2560 CSS px; document width เท่ากับ viewport ทุกขนาด ไม่พบปุ่มล้นจากข้อความอังกฤษ
- PC 1920×1080: body 17px, เมนู 16px, caption 14px, ช่องค้นหา 17px; mobile ช่องกรอก 16px สูง 44px และปุ่มหลักไม่น้อยกว่า 44px
- เลือก Portrait / Chibi / Emotes และชุดสีผ่าน radio; ArrowRight เปลี่ยนสไตล์ได้ มี focus และข้อความสถานะ; ลิงก์เปลี่ยนตาม `kind` และคลิกถึง `/explore?kind=emote` จริง
- ค้นหา `chibi` จากหน้าแรกถึง `/explore?q=chibi` และแสดงคำค้นในช่องกรอก
- Explore, Pricing, For creators, Sign in, หน้าร้านตัวอย่าง: ตรวจ 320, 768, 1024, 1920px ไม่พบทั้งหน้าเลื่อนล้น; ตารางเทียบราคาเลื่อนเฉพาะภายในกรอบตามการออกแบบ
- หน้าบริการตัวอย่าง: ตรวจ 320px และกดถึงขั้นกรอกบรีฟ; input 44px / font 16px; ไม่ส่งคำขอหรือธุรกรรม
- เมนู mobile EN/dark: เปิด/ปิดและอ่านลิงก์ได้
- AppShell, เมนู, Tabs, Input, Textarea, Select, Dialog และบอร์ดว่าง: ตรวจด้วย fixture ชั่วคราวใน local ที่ 320, 390, 768, 1024, 1440, 1920px; หน้าไม่ล้นและแท็บสูงอย่างน้อย 44px
- Dialog ฟอร์มยาวที่ 320×812: กรอบ x=16 ถึง 304, y=16 ถึง 796, เนื้อหา 960px เลื่อนในกรอบสูง 780px ได้; ปิดด้วย Escape ได้
- Fixture ใช้ข้อมูลจำลอง ไม่มีการสร้าง session หรือบันทึกข้อมูล และลบเส้นทางนี้ออกก่อน build/commit
- หน้าแรกไม่มี error ใน browser log ระหว่างตรวจครั้งสุดท้าย

- `pnpm test`: **481 ผ่าน / 0 ไม่ผ่าน**
- `pnpm lint`: ผ่าน
- `pnpm typecheck`: ผ่าน

### ข้อจำกัดและงาน QA ก่อน beta

- ขนาดข้างต้นเป็น CSS viewport บนเบราว์เซอร์ในเครื่อง ไม่ใช่การทดสอบจอ 24 นิ้วจริงทุก resolution/OS scaling และยังไม่ได้ทดสอบ browser zoom 200% จริง
- หลังบ้านตรวจภาพด้วย fixture ของ component จริงและตรวจ source; ยังต้องทดสอบหน้าที่ล็อกอินด้วยบัญชี staging ซึ่งมีออเดอร์จริงในสถานะต่าง ๆ โดยเฉพาะรายละเอียดงาน ไฟล์แนบ การจ่ายเงิน และข้อความยาว
- ยังต้องลองบน iOS Safari / Android Chrome จริง โดยเฉพาะแป้นพิมพ์บนจอ และให้ผู้ใช้งานภาษาไทยประเมินระยะอ่านบนจอของตน
- หน้าแรกในสภาพแวดล้อมที่ตรวจยังไม่มีร้านจริงให้แสดง จึงตรวจ empty state; ต้องเก็บภาพและตรวจการ์ดรายการที่มีข้อมูลจริงอีกครั้งเมื่อมีครีเอเตอร์ beta
- ต้องทดสอบ screen reader และเพิ่มข้อความเป็น 200% แยกก่อนประกาศผ่านมาตรฐาน accessibility; ผลตรวจนี้ไม่ใช่การรับรองทั้งระบบ

## 8. งานต่อหลังเก็บ feedback

1. ให้กลุ่ม beta 5–8 คนลองเลือกสไตล์และค้นหาครีเอเตอร์โดยไม่อธิบายก่อน จดเวลาหาสิ่งที่ต้องการและจุดที่สับสน
2. ถ้าคนเข้าใจ playground ว่าเป็นเครื่องมือสร้างภาพ ให้ปรับคำว่า “ภาพตัวอย่าง” และคำชวนค้นหา ไม่สัญญาว่าสร้างงานส่งมอบให้ได้
3. เมื่อมีร้านจริงที่ยินยอมให้นำงานมาแสดง ค่อยเพิ่มผลงานคัดสรรพร้อมเครดิตและลิงก์กลับร้าน
4. เก็บเหตุการณ์ค้นหา/เลือกหมวด/เข้าร้านตามแผน consent และ privacy ที่ตกลงใน PLAN.md ก่อนติดตั้ง analytics; ไม่เพิ่ม tracking ในงานรอบนี้
5. จัดรอบ QA กับจอ PC ของผู้ใช้และมือถือจริง แล้วปรับความหนาแน่นเนื้อหาจากปัญหาที่พบ
