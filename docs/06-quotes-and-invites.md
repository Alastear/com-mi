# 06 — ใบเสนอราคาและการเชิญลูกค้า

สถานะ: **ตัดสินใจแล้ว ยังไม่ได้สร้าง** (ยกเว้นด่านจ่ายเงินซึ่งขึ้น production แล้ว)

เอกสารนี้มีไว้เพราะแผนนี้เคยอยู่แค่ในบทสนทนา — สิ่งที่ตัดสินใจไปแล้วและ**เหตุผล**
ต้องอยู่ในโปรเจกต์ ไม่งั้นคนถัดไป (หรือ agent ตัวถัดไป) จะเริ่มจากศูนย์
และมีโอกาสสูงที่จะสรุปคนละอย่างกับที่เคยตกลงไว้

---

## 1. สิ่งที่เจ้าของตัดสินใจแล้ว

1. **ก.** ครีเอเตอร์ตั้ง/แก้ราคาบนคำขอที่ลูกค้าส่งเข้ามาแล้ว แล้วส่งกลับเป็นใบเสนอราคา
2. **ข.** ครีเอเตอร์สร้างใบงานเองได้สำหรับคนที่คุยกันมาจาก X / Discord / LINE
   ซึ่ง **อาจยังไม่มีบัญชีในระบบ**
3. **ทุกออเดอร์ต้องผ่านการตอบรับของครีเอเตอร์ก่อนลูกค้าจ่ายได้**

ข้อ 3 ทำเสร็จแล้ว — `canPay()` ใน `lib/orders/release.ts` และด่านใน `recordPayment`

---

## 2. ความจริงที่ตรวจแล้วในโค้ด — อย่าเดาใหม่

**`order.clientUserId` คือตัวตัดสินสิทธิ์ ไม่ใช่แค่ฟิลด์อ้างอิง**
ความเท่ากันของค่านี้ตัดสิน "คุณเป็นใครกับออเดอร์ใบนี้" ใน 6 จุด:

| ไฟล์ | ทำอะไร |
| --- | --- |
| `lib/queries/orders.ts:27` | `getOrderForClient` — เงื่อนไขใน where |
| `lib/queries/orders.ts:81` | `listOrdersForClient` |
| `lib/orders/actions.ts:79` | หา actor ใน `transitionOrder` |
| `lib/orders/actions.ts:228` | หาบทบาทตอนส่งข้อความ |
| `lib/orders/actions.ts:272` | หาบทบาทอีกจุด |
| `lib/payments/actions.ts:51` | `resolveOrder` |
| `lib/delivery/actions.ts:55` | `resolve` |

ทำให้เป็น nullable = อ่อนลงพร้อมกันทั้งหมด และ **ออเดอร์ที่ส่งถึงใครสักคน
จะมองไม่เห็นสำหรับคนนั้นเอง** เพราะ `NULL` ไม่เท่ากับอะไรเลย

**`createOrder` ถือกฎที่ไม่มีใครถืออีก** — ห้ามสั่งงานร้านตัวเอง · ร้านต้องเผยแพร่และเปิดรับ ·
โควตาของแพ็กเกจ · rate limit · `dueAt` จาก `deliveryDays` · แช่ `revisionsAllowed` ·
retry ตอนรหัสออเดอร์ชนกัน · และ **แช่ `tosSnapshot` + `acceptedTosAt`**
ทางสร้างออเดอร์ทางอื่นต้องตอบให้ได้ทุกข้อว่าเก็บไว้ เปลี่ยน หรือจงใจไม่มี

**ไม่มีโค้ดที่ไหนเขียน `order.totalCents` ได้เลยนอกจาก `createOrder`**
สถานะ `quoted` กับเส้นทาง `requested → quoted → accepted` มีอยู่ครบใน state machine
แต่กดปุ่ม "ส่งใบเสนอราคา" วันนี้ **แค่เปลี่ยนสถานะโดยราคาไม่ขยับ**
เป็นบั๊กชนิดเดียวกับปุ่มส่งงานที่ส่งได้โดยไม่มีไฟล์ (แก้ไปแล้ว)

**`service.mode = "proposal"`** มีใน type แต่ไม่มีโค้ดไหนอ่าน — เป็น config ตาย

## 3. แบบ ก. — ใบเสนอราคาบนคำขอที่มีอยู่ ✅ สร้างแล้ว

> **สถานะ: ใช้งานได้จริงแล้ว** — `lib/orders/quote.ts`, `components/app/quote-builder.tsx`,
> `components/app/quote-card.tsx`, ตาราง `order_quote` (migration 0016)
>
> เดินจบทั้งวงบนเบราว์เซอร์จริง: ครีเอเตอร์แก้ ฿1,000 → ฿1,750 เพิ่มบรรทัด ฿500
> เลือกมัดจำ 50% → ลูกค้าเห็นใบและกดยอมรับ → ออเดอร์เป็น `accepted`
> `total_cents` 225000 `deposit_cents` 112500 บรรทัดบนออเดอร์ถูกแทนด้วยของใหม่
> ครบทั้งสามเอกลักษณ์ แจ้งเตือนถึงอีกฝ่ายทั้งสองทาง
>
> **ด่านที่ยิงจริงแล้วว่าไม่หลุด**
> - ใบถูกแทนที่ระหว่างลูกค้าเปิดหน้าค้างไว้ แล้วกดยอมรับ → `superseded`
>   ออเดอร์ไม่ถูกแตะเลย (ยังเป็น `quoted` ราคาเดิม มัดจำ 0)
> - ใบหมดอายุ → การ์ดขึ้นว่าหมดอายุ ปุ่มกดไม่ได้ และด่านฝั่งเซิร์ฟเวอร์ยังกันซ้ำอีกชั้น
>
> **สิ่งที่ได้มาด้วยโดยไม่ได้ตั้งใจ:** `depositCents` มีคนเขียนเป็นครั้งแรก
> ก่อนหน้านี้เป็น 0 เสมอ ด่าน `depositSatisfied()` จึงไม่เคยทำงานสักครั้ง
> ทั้งที่ร่างข้อตกลงตั้งต้นเขียนว่าเก็บมัดจำ 50%
>
> **เส้นทางที่ต้องเพิ่มในเครื่องสถานะ:** `requested → quoted` (ครีเอเตอร์)
> เดิมไม่มี ครีเอเตอร์จึงต้องกด "กำลังดู" ที่ไม่มีความหมายกับใครก่อนหนึ่งครั้ง
> เจอตอนกดจริงในเบราว์เซอร์ ไม่ใช่ตอนอ่านโค้ด — เทสต์คุมไว้แล้ว

### สิ่งที่ยังไม่ได้ทำในแบบ ก.

- ไม่มีปุ่ม "ยกเลิกใบ" ให้ครีเอเตอร์ — ตอนนี้แก้ได้ทางเดียวคือออกใบใหม่ทับ
- ใบที่หมดอายุไม่มีใครไปปิด รอ cron ที่ยังไม่มี (ด่านตอนกดยอมรับกันไว้อยู่แล้ว)



### กฎที่ทั้งหมดย่อลงมาเหลือประโยคเดียว

> ครีเอเตอร์ **ตั้งราคา** ได้ แต่ต้องไม่มีทางไหนที่ครีเอเตอร์ **เขียน** `order.totalCents` ได้
> คนเขียนราคาคือ **ลูกค้าตอนกดยอมรับ** และการกดนั้นต้องระบุว่ากำลังยอมรับใบไหน

ถ้าใช้ปุ่มเปลี่ยนสถานะ `quoted → accepted` ธรรมดาเป็นตัวรับ มันไม่พกราคาไปด้วย
ครีเอเตอร์ที่แก้ราคาขึ้นตอนลูกค้าเปิดหน้าค้างไว้จะผูกลูกค้ากับตัวเลขที่ไม่เคยอ่าน —
**แถวที่ตั้งราคาต้องเป็นแถวเดียวกับที่บันทึกว่าใครตกลงอะไรเมื่อไร**

### การอนุมัติมีสองทาง

- **ไม่แก้ราคา** → รับงานเลย ลูกค้าจ่ายได้ทันที (ไม่เพิ่มขั้นตอนให้ใคร)
- **แก้ราคา** → กลายเป็นใบเสนอราคา ลูกค้าต้องกดยอมรับก่อน เพราะตัวเลขเปลี่ยนแล้ว
  ต้องมีการยินยอมใหม่

### เอกลักษณ์ที่ห้ามพัง (เทสต์คุมอยู่แล้วใน `lib/orders/orders.test.ts`)

1. `totalCents === subtotalCents + addonsCents`
2. ผลรวม `order_item.unitPriceCents × quantity` เท่ากับ `totalCents`
3. ทุกยอดลงตัวเป็นบาท (`formatMoney` ใช้ `cents % 100` ตัดสินว่าจะโชว์ทศนิยม)

## 4. แบบ ข. — เชิญแล้วให้ลูกค้ามารับเอง

### รูปแบบ

ครีเอเตอร์ร่างใบงาน → **ยังไม่มีแถว `order` เกิดขึ้น** → ได้ลิงก์ไปวางใน DM →
ลูกค้าเปิดดูว่าถูกเสนออะไร → ล็อกอิน → กดรับ → **ตอนนั้นออเดอร์ถึงเกิด**
โดยลูกค้าเป็นคนกดยอมรับเอง การยินยอมจึงเป็นของจริง ไม่ใช่ที่แพลตฟอร์มสร้างแทน

`order.clientUserId` ไม่ต้องแก้เลย

### สถานะปลายทางไม่เท่ากัน — จุดสำคัญที่สุดของแบบนี้

```
addressed = ใบเชิญระบุอีเมลไว้
         && ผู้กดรับมีอีเมลยืนยันแล้ว
         && อีเมลตรงกัน
status = addressed ? "accepted" : "requested"
```

`canPay()` เริ่มที่ `accepted` และไม่รวม `requested` ดังนั้น
**ลำพังถือลิงก์ไม่มีทางไปถึงออเดอร์ที่จ่ายเงินได้** คนผิดจะถูกจับบนหน้าจอที่ครีเอเตอร์
เห็นชื่อกับอีเมลของคนที่มากด ก่อนเงินจะขยับ

### แก้ใบงานแล้วต้องไม่เปลี่ยนลิงก์

บัมพ์เลขเวอร์ชันข้อตกลงแทน แล้วให้ฟอร์มยืนยันกลับมา ถ้าไม่ตรงให้ตอบ `terms_changed`
(วินัยเดียวกับ `where status = from` ใน `transitionOrder`)
ลิงก์ที่วางใน DM ไปแล้วจึงไม่ตาย — ซึ่งเป็นความยุ่งยากที่ฟีเจอร์นี้มีไว้แก้ตั้งแต่แรก

### ⚠️ ผลโจมตี — แบบข้างบนยังใช้ไม่ได้ตามที่เขียน

รอบแรกล้มทั้งสามตัว รันใหม่แล้วเจอของจริงระดับ **major**:

> **"สถานะปลายทางไม่เท่ากัน" แค่เลื่อนความเสียหายออกไปหนึ่งการกด
> และเป็นการกดที่ครีเอเตอร์ไม่มีทางรู้ว่าควรกดไหม**

เหตุผลที่รับฟังได้และตรวจแล้วว่าจริง:

- **หน้าจอครีเอเตอร์ไม่แสดงอะไรที่แยกคนถูกจากคนผิดได้เลย** การ์ดบนบอร์ดโชว์แค่ชื่อกับรูป
  ซึ่งเป็นค่าที่คนกดรับตั้งเองได้ทั้งคู่ (ชื่อ Google) · `getOrderForCreator` **ดึงอีเมล
  มาแล้ว** แต่ส่งเข้า `UserAvatar` ซึ่งทิ้งอีเมลทันทีที่มีรูป — อีเมลจึงถูกดึงมาโดยไม่ได้ใช้
  และค่า `addressed` ที่คำนวณได้ก็ถูกทิ้งทันทีที่เลือกสถานะ
- **ความเสียหายเกิดตั้งแต่ก่อนกดรับ** — ตรวจแล้ว: `getOrderForClient`
  (`lib/queries/orders.ts:22`) **ไม่กรองสถานะ** และคืน `promptpayId` + `promptpayName`
  ให้ทุกคนที่เป็น `clientUserId` คนที่แย่งรับจึงอ่านบรีฟทั้งหมดและ**เลขพร้อมเพย์กับชื่อจริง
  ของครีเอเตอร์**ได้ทันที — ข้อมูลชุดเดียวกับที่เพิ่งอุดไม่ให้หลุดหน้าร้านสาธารณะ
- **ย้อนไม่ได้** `clientUserId` มีที่เขียนที่เดียวคือ `create.ts:147` ไม่มีทางย้ายเจ้าของ
  ไม่มีการลบออเดอร์ และ `declined` ก็ไม่ตัดสิทธิ์อ่านเพราะ query ไม่ดูสถานะ
  ส่วนลูกค้าตัวจริงถูกล็อกออกถาวรเพราะ token ถูกใช้ไปแล้ว

**ทางแก้ที่รับมา: ปฏิเสธ ไม่ใช่ลดชั้น**
ถ้าใบเชิญระบุอีเมลไว้แล้วคนกดไม่ตรง → ตอบ `wrong_account` และ **ไม่เผาใบเชิญ**
บอกให้ล็อกอินด้วยอีเมลนั้น อีเมลจึงกลายเป็นด่านจริงไม่ใช่แค่ป้ายกำกับ
เหลือ `requested` ไว้เฉพาะใบเชิญที่ **ไม่ได้ระบุอีเมล** ซึ่งครีเอเตอร์เลือกเองว่า
"ใครถือลิงก์ก็รับได้" · เพิ่ม `revokedAt` ให้เพิกถอนลิงก์ที่ส่งผิดได้ ·
และแสดงอีเมลของคนกดรับบนหน้าออเดอร์ (ดึงมาอยู่แล้ว แค่ไม่ได้แสดง)

### เรื่องที่เจอพ่วงมา — `depositCents` ไม่มีใครเขียนเลย

ตรวจแล้ว: ไม่มีโค้ดที่ไหน `set`/`insert` ค่านี้ มันคงเป็น `0` ตลอด แปลว่า
`depositSatisfied()` เป็นจริงเสมอ และด่านมัดจำใน `transitionOrder` ไม่เคยทำงาน
ทั้งที่ข้อตกลงตั้งต้นเขียนว่า "ชำระมัดจำ 50% ก่อนเริ่มงาน" — ต้องเลือกว่าจะทำให้ใช้ได้จริง
หรือเอาออกจากข้อความ ไม่ควรค้างแบบนี้

### ข้ออ้างที่ตรวจแล้วว่า "เกินจริง"

รายงานบอกว่าอีเมลตัวพิมพ์ใหญ่-เล็กเป็นช่องโหว่ (`Bob@x.com` กับ `bob@x.com` เป็นคนละบัญชี)
— **ไม่จริง** Better Auth ทำ `toLowerCase()` ตอนสมัคร (`dist/api/routes/sign-up.mjs:165`)
และข้อมูลจริงไม่มีเคสนี้ ยัง**ควร**เพิ่ม unique index บน `lower(email)` กันไว้ แต่ไม่ใช่เรื่องด่วน

## 4.5 ผลโจมตีรอบสอง — ทางแก้ที่รับมายังไม่ผ่าน (13 ส.ค. 2026)

โจมตีซ้ำตามที่บันทึกไว้ว่าต้องทำก่อนสร้าง ผลคือ **ยังสร้างไม่ได้** เหลือ 4 ข้อที่ต้องแก้แบบ
ก่อน ไม่ใช่แก้ตอนเขียนโค้ด

### B1 — ทางกดรับต้องไม่มี `insert(order)` ตัวที่สอง

`lib/orders/create.ts` ถือกฎไว้คนเดียวหกข้อ: ห้ามสั่งร้านตัวเอง (`:87`) · ร้านต้องเผยแพร่แล้ว
(`:101`) · ไม่ถูกผู้ดูแลระงับ (`:104`) · สถานะร้านรับงาน (`:105`) · ลิมิตต่อผู้ใช้ (`:70-77`) ·
`dueAt` จาก `service.deliveryDays` (`:141`) · แช่ `tosSnapshot` + `acceptedTosAt` (`:156-157`)

แบบที่เขียนไว้สร้างออเดอร์ตอนกดรับ ซึ่งอยู่นอกฟังก์ชันนั้น กฎทั้งหกจึงต้องถูกคัดลอกด้วยมือ
และจะเน่าเงียบ ๆ **ที่ต้องแก้ในแบบ:** ระบุให้ชัดว่าต้องแยก `insertOrder()` /
`assertCanAcceptNewOrder()` ออกมาจาก `createOrder` ก่อน แล้วทางกดรับเรียกตัวนั้น
เคสที่บล็อกจริง: ใบเชิญระบุอีเมลลงที่ `accepted` ซึ่ง `canPay()` เปิดทันที — ร้านที่ถูกระงับ
หลังส่งลิงก์ไปแล้วจะขึ้น QR พร้อมเพย์ของคนที่ถูกแบน และ `tosSnapshot` ว่างทำให้การ์ดข้อตกลง
หายไปทั้งใบโดยไม่มีใครสังเกต

### B2 — ใบเชิญที่ไม่ระบุอีเมลต้องไม่สร้างออเดอร์ตอนคลิก

`order.clientUserId` เป็น `notNull` มีที่เขียนที่เดียว และ**ไม่มี `delete` ออเดอร์ที่ไหนเลย**
คลิกแรกของคนที่ได้ลิงก์ต่อ ๆ กันมาจึงผูกออเดอร์กับคนนั้นถาวร และคนนั้นกด `cancelled` ได้ทันที
ซึ่งเป็นสถานะปลายทาง ครีเอเตอร์ต้องร่างใหม่ตั้งแต่ต้น

(ข้ออ้างเดิมเรื่อง "อ่านเลขพร้อมเพย์ได้ทันที" **ตรวจแล้วไม่จริง** — ที่ `requested`
`canPay()` เป็นเท็จ หน้าจึงหยุดที่การ์ดรอตอบรับ ไม่เคยไปถึงส่วน QR ความเสียหายคือ
การผูกที่แก้ไม่ได้กับการยกเลิกที่ย้อนไม่ได้ ไม่ใช่ข้อมูลรั่ว)

**ที่ต้องแก้ในแบบ:** คลิกแล้วเขียนแค่ `invite_claim(inviteId, userId, claimedAt)`
แล้วให้ครีเอเตอร์กดยืนยันเองโดยเห็นอีเมลคนกด — ให้ใบที่ไม่ระบุอีเมลได้คุณสมบัติเดียวกับ
ใบที่ระบุ คือ "ครีเอเตอร์เห็นว่าเป็นใครก่อนที่อะไรจะผูก"

### B3 — "บัมพ์เลขเวอร์ชัน" เป็นเครื่องมือผิด ใช้ตัวตนของแถวแทน

ที่เก็บนี้แก้ปัญหาเดียวกันไปแล้วและแก้ได้ดีกว่า: `acceptQuote` รับ `quoteId` ปฏิเสธใบที่
`supersededAt`/`acceptedAt` และออกใบใหม่ = แถวใหม่ทับแถวเก่า ไม่ใช่เขียนทับ
พร้อม partial unique index บังคับว่ามีใบเปิดอยู่ใบเดียว เลขนับบนแถวที่แก้ทับได้
แยก v3 → v4 → กลับมา v3 ไม่ออก และไม่เหลือหลักฐานว่าตกลงอะไรกันจริง
**ที่ต้องแก้ในแบบ:** `order_invite_revision` เขียนเพิ่มอย่างเดียว แบบเดียวกับ `order_quote`

## 4.6 แบบร่างที่สอง — เขียนใหม่ตามผลโจมตี (ยังไม่ได้สร้าง)

### รูปทรง

```
ครีเอเตอร์ร่างใบเชิญ → ได้ลิงก์ไปวางใน DM
ลูกค้าเปิด → เห็นว่าถูกเสนออะไร ราคาเท่าไร → ล็อกอิน → กด "รับงานนี้"
   ↓
เขียนแค่แถว invite_claim — **ยังไม่มีออเดอร์**
   ↓
ครีเอเตอร์เห็นบนบอร์ดว่าใครมากด (พร้อมอีเมล) → กดยืนยัน
   ↓
ออเดอร์เกิดผ่าน insertNewOrder() ตัวเดียวกับที่ลูกค้าสั่งเอง
```

### ตอบ B1 — ไม่มี `insert(order)` ตัวที่สอง

**ทำแล้ว** `lib/orders/new-order.ts` ถือทั้ง `assertCanAcceptNewOrder()` และ
`insertNewOrder()` มีเทสต์เชิงโครงสร้างคุมว่าทั้งโปรเจกต์มี `insert(schema.order)`
ที่เดียว ทางกดรับต้องเรียกสองตัวนี้ ห้ามเขียนเอง

**ด่านต้องถูกตรวจตอนครีเอเตอร์กดยืนยัน ไม่ใช่ตอนสร้างใบเชิญ** — ระหว่างสองจังหวะนั้น
ร้านอาจถูกระงับ ปิดรับงาน หรือโควตาเต็มไปแล้ว

### ตอบ B2 — คลิกแล้วยังไม่ผูกอะไร

`invite_claim(id, inviteId, userId, claimedAt, rejectedAt)` — คลิกแล้วเขียนแค่นี้
`order.clientUserId` เป็น `notNull` เขียนที่เดียว และ **ไม่มี `delete` ออเดอร์ที่ไหนเลย**
การผูกจึงถาวรตั้งแต่วินาทีแรก ต้องไม่ให้คนแปลกหน้าที่ได้ลิงก์ต่อ ๆ กันมาเป็นคนกดผูก

- ใบที่ **ระบุอีเมล** → คนที่อีเมลไม่ตรงกดรับไม่ได้เลย ตอบ `wrong_account`
  และ **ไม่เผาใบ** บอกให้ล็อกอินด้วยอีเมลนั้น
- ใบที่ **ไม่ระบุอีเมล** → ใครกดก็ได้ แต่ได้แค่ `invite_claim` ครีเอเตอร์เป็นคนกดยืนยัน
  โดยเห็นชื่อกับอีเมลของคนกด (ดึงมาอยู่แล้วที่ `lib/queries/orders.ts` แค่ไม่ได้แสดง)
- `revokedAt` เพิกถอนลิงก์ที่ส่งผิดได้ · ใบมีวันหมดอายุเหมือน `order_quote`

### ตอบ B3 — ใช้ตัวตนของแถว ไม่ใช่เลขนับ

`invite_revision` เขียนเพิ่มอย่างเดียว แบบเดียวกับ `order_quote` เป๊ะ:
partial unique index ให้มีฉบับเปิดอยู่ฉบับเดียวต่อใบเชิญ · แก้ราคา = ออกฉบับใหม่
ทับฉบับเก่า ไม่ใช่เขียนทับ · ปุ่มกดรับส่ง `revisionId` ไปด้วยเสมอ
ฉบับที่ถูกแทนแล้วกดไม่ผ่าน ตอบ `superseded` แล้วรีเฟรชให้อ่านฉบับใหม่

เหตุผลไม่ใช่ทฤษฎี — เป็นสิ่งเดียวกับที่ `acceptQuote()` ทำอยู่แล้ว และคอมเมนต์ที่นั่น
เขียนภัยไว้ตรง ๆ ว่า "ลูกค้าเปิดหน้าค้างไว้ ครีเอเตอร์ขึ้นราคา ลูกค้ากดปุ่มเก่าที่ค้างอยู่"

### สี่คำถามที่ค้างไว้ — ตอบแล้วจากผลโจมตีรอบสอง

**1. หน้าพรีวิวโชว์อะไร** — ข้อเสนอ แต่ไม่บอกอะไรเกี่ยวกับผู้รับเลย
ชื่อร้าน/handle/รูป (สาธารณะอยู่แล้ว) · ชื่อบริการ · บรรทัดราคาและยอดรวม · มัดจำ ·
กำหนดส่งและจำนวนรอบแก้ที่แช่ไว้ · ข้อตกลงฉบับที่แช่ · ข้อความจากครีเอเตอร์ · วันหมดอายุ
**ห้ามโชว์อีเมลที่ระบุไว้ แม้แต่แบบปิดบางส่วน** — เจ้าตัวไม่ต้องถูกบอกอีเมลตัวเอง
และการแสดงมันเปลี่ยนลิงก์ให้กลายเป็นเครื่องมือตรวจอีเมลของคนที่ได้ลิงก์ต่อมา
ข้อความตอนอีเมลไม่ตรงจึงบอกแค่ "ใบเชิญนี้ออกให้อีเมลอื่น" ไม่เอ่ยอีเมลใด

**2. ใบที่ไม่ระบุอีเมล — ไม่ทำ ทุกใบต้องมีอีเมล**
เหตุผลที่ตัดสิน: อีเมลเป็นฟิลด์เดียวที่ผู้ใช้เปลี่ยนเองไม่ได้ในระบบนี้
(`/update-user` ปฏิเสธอีเมล และเส้นทางเปลี่ยนอีเมลอยู่ใน `disabledPaths`)
ส่วน**ชื่อกับรูปแก้เองได้ทั้งคู่** — ถ้าไม่มีอีเมลให้เทียบ คุณสมบัติที่ทั้งแบบนี้มีไว้
("ครีเอเตอร์เห็นว่าใครมากดก่อนที่อะไรจะผูก") ก็ไม่ได้บอกอะไรเลย
และที่หนักกว่านั้น: **ปุ่มกดรับบนใบที่ไม่ระบุอีเมลคือการยื่นอีเมลจริงให้คนออกใบ**
โดยหน้าจอบอกว่ากำลัง "รับงาน" ใครมีร้านก็โปรยลิงก์เก็บอีเมลได้ทีละคลิก
ต้นทุนของการบังคับระบุอีเมลคือทัก DM ถามหนึ่งครั้ง · ระบุผิดก็ออกฉบับใหม่ได้
ส่วนอีเมลที่หลุดไปแล้วเรียกคืนไม่ได้

**3. ออเดอร์เริ่มที่ `accepted`** แต่ไปถึงด้วยการอัปเดตแบบมีเงื่อนไขหลังแถวเกิด
`insertNewOrder` ยังเขียน `requested` ตายตัวเหมือนเดิม **ห้ามเพิ่มพารามิเตอร์สถานะ** —
นั่นคือปุ่มที่จะให้ทางเรียกในอนาคตสร้างออเดอร์ที่จ่ายเงินได้โดยไม่มีใครตกลง
ตัวยืนยันทำ `update ... where status='requested'` ต่อท้ายแทน ถ้าพลาดออเดอร์ค้างที่
`requested` แล้วครีเอเตอร์กดปุ่มปกติได้ — ล้มไปทางที่ปลอดภัย
เหตุผลที่ไม่หยุดที่ `requested`: หน้าลูกค้าจะขึ้น "รอครีเอเตอร์ตอบรับ" ให้คนที่ครีเอเตอร์
เพิ่งกดยืนยัน และบอร์ดจะเอาไปวางในคอลัมน์ "คำขอใหม่" ให้กดรับสิ่งที่รับไปแล้ว

**4. การยินยอมเกิดตอนลูกค้ากดรับ** ไม่ใช่ตอนออเดอร์เกิด
`claim.revisionId` เป็น `notNull` และ `order.acceptedTosAt` ต้องเป็น `claim.claimedAt`
ไม่งั้นหลักฐานการยินยอมชิ้นเดียวที่มีจะประทับเวลาการกดของครีเอเตอร์ หลังลูกค้าเป็นวัน

### ห้าจุดที่ต้องแก้ก่อนสร้าง (จากผลโจมตีรอบสอง)

1. **คำขอต้องมีวงจรชีวิต** — `revokedAt` เพิกถอนลิงก์แต่ไม่แตะคำขอที่กดไปแล้ว
   สร้างคำขอด้วยคำสั่งเดียวแบบมีเงื่อนไข (`insert ... select ... where exists (...)`)
   เพิกถอน = `batch` เดียวที่ปิดลิงก์**และ**ปฏิเสธคำขอที่ยังเปิดอยู่ ·
   ยืนยัน = compare-and-set บนใบ ไม่ใช่รายการเงื่อนไขในเอกสาร · เพิ่ม `withdrawnAt`
2. **`insertNewOrder` ต้องรับ `depositCents`** ไม่งั้นออเดอร์จากใบเชิญเกิดมาพร้อม
   ด่านมัดจำที่ตายแล้ว — รูเดิมที่เพิ่งอุดไปตอนทำใบเสนอราคา ✅ ทำแล้ว
3. **ต้องแช่กำหนดส่งกับจำนวนรอบแก้ไว้ในฉบับ** ไม่ใช่อ่านสดตอนยืนยัน ✅ อยู่ในสคีมาแล้ว
4. **ใบต้องระบุว่าชี้ไปที่บริการไหน** และตอนยืนยันต้องอ่านซ้ำด้วยตัวกรอง
   `isActive && deletedAt is null` เดียวกับ `createOrder` — บริการที่ถูกลบระหว่างทาง
   ต้องไม่รอด และครีเอเตอร์ที่ไม่มีบริการเปิดอยู่เลยต้องออกใบไม่ได้
5. **ตอบคำถามข้อ 2 ก่อนตัดสคีมา** เพราะ `email` เป็น `notNull` หรือไม่ เปลี่ยนด่านทุกตัว
   ที่อยู่ถัดจากมัน ✅ ตอบแล้วข้างบน — `notNull`

## 5. ลำดับที่ควรทำ

1. **ก.** ก่อน — ปลอดภัยกว่าและไม่ต้องรออะไร ตัวตนลูกค้า ข้อตกลงที่ยอมรับ และโควตา
   ถูกบันทึกไว้ตั้งแต่ตอนลูกค้ากดสั่งแล้ว
2. **ข.** — **ยังไม่ผ่าน** โจมตีรอบสองแล้ว (ดู §4.5) เหลือ 4 ข้อที่ต้องแก้ที่ตัวแบบก่อน
   สิ่งที่ต้องทำก่อนเขียนโค้ดบรรทัดแรกคือ **แยก `insertOrder()` ออกมาจาก `createOrder`**
   เพราะทั้ง B1 และ B2 ย่อลงมาเหลือเรื่องเดียวกัน: อย่ามีทางสร้างออเดอร์ทางที่สอง
